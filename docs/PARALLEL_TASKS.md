# 独立工作区的有限任务并行

本页路径相对安装了 SOP 的宿主项目根目录；引擎在 `.ai-sop/`。这些规则不要求引入新的调度器、测试环境或每日登记步骤。

## 支持范围

| 场景 | 支持情况 |
|---|---|
| 不同功能、不同工作区 | 支持，包括各自 T3 |
| 同功能、不同工作区，T1/T2 与 T1/T2 | 支持 |
| 同功能、不同工作区，T3 与 T1/T2 | 支持 |
| 同功能、不同工作区，T3 与 T3 | 暂不支持，见后续计划 |
| 同工作区、同功能的多个独立任务 | 串行；先 Suspend/Complete/Cancel，再 Start |

前提是每个工作区都有独立代码、`.ai-workspace`、`specs` 工作副本和不同 TaskId。可用同一 SVN 分支的两个 checkout，最终人工合并；Git 可用独立分支降低规格冲突，但不要求更换版本控制。独立分支或目录名称本身不构成权限隔离；机器本地注册表默认依据物理工作区路径隔离，别用环境变量把两处指向同一注册表，也不要用符号链接或 junction 共用可写规格树。

使用支持 task Schema 1.1 的引擎。旧引擎不能解释新来源字段，不要混用继续写；升级前可运行已有 Preflight。旧 Schema 1.0 的 ACTIVE 记录缺少来源时仍保守阻止 Start；在原工作区暂停并同步，后续 Resume 重新取得归属时会记录来源。原处不可用则确认停止后走恢复，不能手填来源来绕过检查。

## 日常使用

1. 人工选择两项独立目标，确认范围在上表内。两边按通常的 Discover → Start 执行，不需要新的并行命令。默认 T2，人工指定 T1/T3 时按原规则记录请求；TaskId 留空由工具生成，或显式使用不同名称。
2. 各自只完成本任务的档位要求。T1 仍可延期文档/用例并留下 FollowUp；T2 同步实际受影响的规格、用例并运行相关测试，不默认启动完整业务服务。修复现有行为可记录文档 UNCHANGED，但不能把实际契约变化当成不需同步。T3 与轻档并行时，轻档也遵守既有批准失效规则。
3. 每个任务的代码、规格、执行记录各自持久化。`.ai-workspace` 与 `specs` 是嵌套独立 Git 时分别同步，输入清单 `.ai-workspace/specs/.artifacts/` 跟随 specs。Session/Grant/owner、本地 `.runtime/` 不复制为另一工作区的权限。
4. 由人工合并代码、设计文档及测试用例。`tasks/<TaskId>/` 保留各自记录，不把 A 的记录改成 B 的；共享的 `00/04/05/06/07` 等产物要按实际含义处理冲突，不能简单保留“最新时间”或合并绿色状态。合并到活动任务会使受影响证据过期，应重新执行对应验证。如果两项任务已 DONE，可另开默认 T2 的整合任务；需要改变 T3 已批准语义时按原批准流程处理，不自动升档。

单项 DONE 只表示该工作区当时的任务通过，不表示组合后通过。历史 DONE 不因后续合并被改回未完成；新验证绑定合并后的输入。测试数据隔离、共享服务协调不在本次新增范围内，按宿主已有约定使用。

## 能检测什么

`task.json.executionLocation` 保存取得归属时的机器名、规范化物理工作区、时间；它用来区分本地任务和同步观察，不是执行授权。本地 session/owner/任务必须匹配才能写。外部 ACTIVE 在 Discover/Status 中标为 EXTERNAL，不凭本地基线和测试输入宣布它失效，也不要求先 Recover 它才能启动独立轻档。

在已同步的同功能记录中：本地或来源不明的 ACTIVE 返回 `TASK_ACTIVE_CONFLICT`；当前请求 T3 且外部还有 ACTIVE T3 返回 `TASK_PARALLEL_T3_UNSUPPORTED`。Start、Resume/会话绑定、ChangeTier 检查冲突；写前防护与完成检查也检查。暂停、取消、恢复仍可操作，避免冲突后无路可退。

**没有跨机器实时锁。** 如果 A、B 未同步活动记录，各自都可能成功启动 T3；同机两处也不会偷偷扫描所有工程去寻找另一项任务。仅凭 Git/SVN 同分支无法阻止这种情况。启动前人为避免双 T3；同步可见后及时处理，不能把一次 Start 成功解释成远端没有 T3。

## 误开 T3 + T3：保全并恢复

这通常先造成两套规格、批准和验证彼此不一致；在独立工作副本中不会仅因同时运行就覆盖对方文件。真正的风险在盲目合并、覆盖规格或沿用旧证据。机器能恢复任务状态，不能推断哪份业务设计才正确。

1. **先停止继续修改和同步覆盖，保存两边现场。** 各自备份代码、未跟踪文件、规格、任务记录、`.artifacts/` 和相关日志。需要查状态时用 Status/InspectRecovery。不要删除 task/owner、清空门禁、`reset --hard` 或用一侧目录覆盖另一侧。
2. **选一项暂缓，在原工作区暂停。** 对两个任务都暂停后再比较也可以。假设暂缓 B，在 B 的项目根目录执行：

   ```powershell
   pwsh -NoProfile -File ./ai-sop.ps1 Task -Operation Suspend -Feature Example -TaskId task-b -NextAction "合并核对后恢复" -Notes "误开同功能双 T3，已保存两边现场"
   ```

   若还有验证进程运行，先等待结束或正常停止。若 Agent 已退出、会话或归属损坏，先诊断；**确认原执行和验证进程停止后**才恢复：

   ```powershell
   pwsh -NoProfile -File ./ai-sop.ps1 Task -Operation InspectRecovery -Feature Example -TaskId task-b
   pwsh -NoProfile -File ./ai-sop.ps1 Task -Operation Recover -Feature Example -TaskId task-b -ForceRecovery -Reason "已确认原 Agent 和验证进程停止，保留两份现场后恢复"
   ```

   Recover 将任务转成 PAUSED、释放匹配的本地归属，保留工作内容、原基线与可用证据。原工作区不可用时，可以在已同步记录的接收端操作，但依然必须确认来源已停止；ForceRecovery 不是远程停止命令。损坏证据按 InspectRecovery 指引隔离保存，本地仍运行的验证不能强制绕过。

3. **同步暂停事实，保留两份独立任务记录。** 将 B 的 PAUSED 记录以及必需产物同步到 A；不要复制权限注册表，不恢复 B 的旧 ACTIVE 版本。A 再 Resume 原任务可继续；若 A 也已暂停，先同步 A 的暂停事实到 B。后续继续 B 前，先结束或暂停 A 并同步；同功能一次只保留一个 T3 活动。
4. **恢复正确内容，而不只是解除占用。** 对照共同基线和两份备份合并代码、规则、设计和测试；选择与确认设计匹配的批准记录，语义已变化则按正常 ResetApproval/批准流程重新确认。04 绑定当前任务实际差异重新审阅；05 覆盖与用例标识重新核对；06/07 审查哈希必须匹配正确设计。禁止从两份状态里拼出一个“全绿”记录。
5. **重新验证最终输入。** 原任务启动基线不变，不能用当前代码补拍冒充原基线。若可信旧基线丢失，先从备份恢复；确实无法恢复则保留并取消旧任务，明确已存在改动的审查范围后新建整合任务，不能声称新 Start 的差异覆盖此前全部工作。对最终合并内容运行受影响编译/测试并按本档完成校验；重新批准涉及的 T3 产物。Verify/Complete 通过才可报告恢复后的交付通过。

已经误覆盖时，从 SVN/Git 历史、各自工作副本或备份找回原内容，再执行第 4、5 步；没有历史/备份的未提交内容无法保证自动恢复。本流程也不回滚测试已经写入的外部服务数据，外部数据恢复遵循宿主自己的备份方案。

## 后续计划：T3 + T3

暂记录设计难点，不在当前版本增加实现或门禁：

| 难点 | 后续实现前需确定 |
|---|---|
| 功能级 `00` 批准、`06/07` 契约及审查 | 两项 T3 分别批准哪个版本；如何保留原版本、避免一方重置/覆盖另一方批准 |
| 单份 `04` 与任务差异绑定 | 任务级独立影响摘要及历史归档，合并时重新审阅，不能共用一个“最新摘要” |
| `05` 用例计划与覆盖映射 | 稳定条款/CaseId 的冲突处理、任务范围与组合范围，设计变更后如何失效重验 |
| 任务基线与证据 | 各自不可变启动清单、可读取的输入策略版本、合并结果的独立验收；不能转移绿色证据 |
| 同步及故障恢复 | 状态冲突不能按时间自动覆盖，未同步活动不可凭本地文件检测；是否值得引入共享协调服务需单独评估 |
| 开发体验与迁移 | 尽量复用 Start/Resume/Suspend，明确旧任务/旧引擎兼容、回退与可恢复备份；避免让 T1/T2 承担额外流程 |

未来即使开放 T3 + T3，两个 T3 都通过也不等于合并后通过。优先用真实冲突案例验证是否需要这项支持，再决定是否承担任务级规格版本化和整合验收成本。
